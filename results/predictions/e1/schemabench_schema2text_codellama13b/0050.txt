The schemabench_0050 database contains 22 tables, each representing a different entity or relationship in the system. The tables are:
1. attachments: This table stores information about attachments, including the file path, the ID of the attachable entity (e.g. a ticket or a lead), and the type of attachable entity.
2. comments: This table stores information about comments, including the ID of the ticket or lead being commented on, the user who made the comment, the comment body, and the date and time the comment was made.
3. failed_jobs: This table stores information about failed jobs, including the connection, queue, payload, exception, and date and time the job failed.
4. ideas: This table stores information about ideas, including the requester ID, status, title, repository, issue ID, due date, body, development effort, sales impact, current impact, and whether the idea is deleted.
5. kpis: This table stores information about key performance indicators (KPIs), including the date, type, KPI, relation ID, total, and count.
6. lead_status_updates: This table stores information about lead status updates, including the new status, body, lead ID, user ID, and date and time the update was made.
7. leads: This table stores information about leads, including the email, status, team ID, user ID, name, body, username, address, city, country, postal code, company, phone, and whether the lead is deleted.
8. memberships: This table stores information about memberships, including the user ID, team ID, admin status, and date and time the membership was created.
9. merged_tickets: This table stores information about merged tickets, including the ticket ID, merged ticket ID, and date and time the ticket was merged.
10. migrations: This table stores information about migrations, including the migration name and batch number.
11. password_resets: This table stores information about password resets, including the email, token, and date and time the reset was requested.
12. requesters: This table stores information about requesters, including the name, email, and whether the requester is a no-reply.
13. settings: This table stores information about settings, including the Slack webhook URL, default team ID, and date and time the setting was created.
14. taggables: This table stores information about taggables, including the tag ID, taggable ID, and taggable type.
15. tags: This table stores information about tags, including the name, created date, and updated date.
16. tasks: This table stores information about tasks, including the lead ID, user ID, body, datetime, completed status, and date and time the task was created.
17. teams: This table stores information about teams, including the name, email, Slack webhook URL, token, and date and time the team was created.
18. ticket_events: This table stores information about ticket events, including the ticket ID, user ID, body, and date and time the event was created.
19. ticket_types: This table stores information about ticket types, including the name, color, and date and time the type was created.
20. tickets: This table stores information about tickets, including the title, body, public token, requester ID, team ID, user ID, status, priority, level, rating, created date, updated date, deleted date, ticket type ID, subject, and summary.
21. user_settings: This table stores information about user settings, including the user ID, daily tasks notification, tickets signature, new ticket notification, ticket assigned notification, ticket updated notification, new lead notification, lead assigned notification, new idea notification, mention notification, ticket rated notification, and date and time the setting was created.
22. users: This table stores information about users, including the name, email, locale, password, admin status, assistant status, remember token, created date, updated date, can see reports, and token.
Each table has its own set of columns, with some tables having foreign keys that reference other tables. The tables are related to each other through these foreign keys, which ensure that the data is consistent and accurate. For example, the tickets table has a foreign key to the ticket types table, which ensures that each ticket has a valid ticket type. Similarly, the comments table has a foreign key to the tickets table, which ensures that each comment is associated with a valid ticket. The foreign keys also ensure that the data is consistent and accurate, as they enforce referential integrity.
